# 1. Production backend и эволюция Go

## Введение

На первой лекции важно сразу убрать опасную иллюзию: если программа компилируется, запускается и отвечает `200 OK`, это ещё не означает, что мы получили production backend.

Локально всё может выглядеть идеально:

```text
HTTP request
↓
handler
↓
service
↓
repository
↓
PostgreSQL
↓
200 OK
```

Но реальная система живёт в другой среде. Запросы приходят одновременно. Процессы перезапускаются. Несколько версий приложения какое-то время работают параллельно. База данных тормозит. Внешний API отвечает через пять секунд вместо пятидесяти миллисекунд. Соединения заканчиваются. Клиент не получает ответ и повторяет запрос. Ошибка может случиться после того, как часть операции уже была выполнена.

Поэтому центральный вопрос этой лекции:

> Что позволяет доверить программе реальные запросы?

Ответ лежит не только в синтаксисе Go. Нужно понимать, как приложение собирается, что именно разворачивается, чем отличаются окружения, где хранится конфигурация, от каких внешних ресурсов зависит сервис, как Go эволюционировал как production-платформа и какие гарантии действительно даёт язык и toolchain.

---

## Как читать эту лекцию

Материал построен слоями. Сначала рассматриваем backend как эксплуатируемую систему: окружения, артефакт, конфигурацию и внешние зависимости. Затем разбираем, почему Go как язык и платформа эволюционировал именно в таком направлении. После этого отдельно закрепляем три механизма, которые нужны практически в любом современном Go-проекте: compatibility promise, modules/generics и toolchain.

У каждого механизма нас интересуют четыре вопроса:

```text
какую проблему решает?
↓
как устроена ментальная модель?
↓
какие ограничения и компромиссы?
↓
что это меняет в production backend?
```

Поэтому дальше некоторые вещи будут разобраны глубже, чем требуется просто для написания синтаксически правильного Go-кода.

# 1. Production backend

## 1.1. Что такое production

Production — это среда, где система выполняет реальную работу для пользователей или других систем.

Ключевой признак production — последствия.

Если ошибка приложения может:

- потерять данные;
- создать дубликат;
- сорвать бизнес-процесс;
- сделать функцию недоступной;
- нарушить интеграцию с другой системой;
- привести к финансовым или операционным последствиям;

то речь уже идёт о production-нагрузке, даже если приложение работает на одном сервере и обслуживает десять человек.

И наоборот: огромный тестовый кластер из сотни машин остаётся тестовым, если он не обслуживает настоящую работу.

Поэтому production определяется назначением системы, а не количеством серверов.

## 1.2. Почему успешный HTTP-запрос почти ничего не доказывает

Возьмём простейший сервер:

```go
package main

import (
    "fmt"
    "net/http"
)

func main() {
    http.HandleFunc("/hello", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "hello")
    })

    if err := http.ListenAndServe(":8080", nil); err != nil {
        panic(err)
    }
}
```

Он компилируется, запускается и отвечает:

```bash
curl http://localhost:8080/hello
```

```text
hello
```

Это подтверждает только один сценарий:

```text
процесс запустился
+
порт доступен
+
handler отработал
+
ответ дошёл до клиента
```

Ничего из этого не проверяет отказ базы данных, задержку внешнего API, перегрузку, нехватку соединений, корректность retry, повтор запроса, rolling update, graceful shutdown и диагностику после сбоя.

Production начинается там, где happy path перестаёт быть единственным рассматриваемым сценарием.

## 1.3. Частичный успех

Рассмотрим создание заказа.

```text
1. HTTP handler принимает запрос
2. PostgreSQL сохраняет заказ
3. приложение публикует событие OrderCreated
4. клиент получает ответ
```

Идеальный сценарий:

```text
request
↓
INSERT
↓
COMMIT
↓
publish
↓
200 OK
```

Теперь ломаем публикацию:

```text
request
↓
INSERT
↓
COMMIT
↓
publish
↓
ERROR
```

Заказ уже существует, но событие не опубликовано.

Если клиент получает `500`, он может повторить запрос:

```text
request #1
→ order created
→ response failed

request #2
→ order created again
```

Так появляется дубликат.

Отсюда фундаментальный принцип backend:

> Ошибка ответа не означает, что операция ничего не сделала.

То же относится к timeout. Если клиент перестал ждать ответ, это не доказывает, что удалённая система не обработала запрос. Timeout означает только прекращение ожидания результата.

Именно поэтому в production появляются отдельные инженерные темы: идемпотентность, retry, транзакции, outbox, дедупликация и восстановление после частичного выполнения.

Go сам по себе не делает независимые операции атомарными.

---

## 1.4. Production как набор инженерных обязательств

Удобно мыслить production не как «сервер где-то в дата-центре», а как набор обязательств системы перед внешним миром. У backend обычно есть как минимум четыре измерения качества:

```text
correctness   — результат операции логически корректен
availability  — систему можно использовать тогда, когда она нужна
latency       — ответ приходит за приемлемое время
operability   — проблему можно обнаружить, локализовать и объяснить
```

Эти свойства связаны. Например, можно повысить availability агрессивными retry и одновременно уничтожить latency перегруженной зависимости. Можно ускорить запрос кешированием и получить проблему consistency. Можно вернуть `200 OK` очень быстро, но потерять событие, необходимое другой системе.

Поэтому production-разработка почти всегда состоит из компромиссов. Нас интересует не только «работает ли код», но и **какое поведение система демонстрирует при отклонении от happy path**.

### Жизненный цикл одного запроса

Даже простой HTTP-запрос проходит несколько границ:

```text
client
↓
TCP / TLS
↓
HTTP server
↓
handler
↓
application logic
↓
DB pool / HTTP client pool
↓
external resource
↓
обратный путь ответа
```

На каждой границе есть собственная очередь, собственный timeout и собственное ограничение capacity. Из-за этого симптом в одном месте может быть вызван bottleneck совершенно в другом.

Пример: handler выполняется медленно, но CPU процесса почти свободен. Это не противоречие. Goroutine может большую часть времени ждать свободное соединение из пула или ответ БД. С точки зрения CPU она почти ничего не делает, но с точки зрения пользователя запрос всё равно медленный.

### Ошибка, отказ и деградация — разные ситуации

Полезно различать три режима:

```text
ошибка       — конкретная операция завершилась неуспешно
отказ        — компонент не способен выполнять свою функцию
деградация   — функция выполняется, но хуже ожидаемого уровня
```

Например, PostgreSQL может не быть «упавшей»: она отвечает, но вместо 20 мс запрос занимает 8 секунд. Для пользователя это уже практически отказ, хотя TCP-соединение установлено и SQL в итоге выполняется.

### Почему observability входит в production-модель

Локально разработчик видит программу непосредственно. В production проблема часто расследуется после события. Поэтому система должна оставлять следы:

- логи — что произошло;
- метрики — как менялось состояние во времени;
- traces — где конкретный request провёл время;
- версия артефакта — какой код вообще работал.

Если сервис тормозит, а у нас есть только строка `request failed`, проблема почти не диагностируема. Production-ready система должна позволять восстановить причинную цепочку хотя бы постфактум.

# 2. Dev / Test / Stage / Prod

Разные окружения существуют не ради названий. Каждое проверяет свой набор предположений.

| Среда | Назначение | Типичные условия |
|---|---|---|
| Dev | Быстрая разработка | Отладчик, локальные сервисы, частые изменения |
| Test | Автоматическая проверка | Контролируемые сценарии и данные |
| Stage | Репетиция релиза | Интеграции и topology близки к production |
| Prod | Реальная работа | Настоящие данные, нагрузка и обязательства |

## 2.1. Dev

Dev-среда оптимизирована под скорость разработки. Здесь нормальны debugger, mock-сервисы, локальная PostgreSQL, упрощённая конфигурация, подробное логирование и частые перезапуски.

Главная задача dev:

```text
изменил код
↓
быстро запустил
↓
быстро проверил гипотезу
```

Но dev почти никогда не воспроизводит настоящую topology и нагрузку production.

## 2.2. Test

Test-среда нужна для воспроизводимых проверок:

```text
build
↓
unit tests
↓
integration tests
↓
API tests
```

Тестовая среда должна быть достаточно контролируемой, чтобы результат зависел прежде всего от программы, а не от случайного состояния окружения.

## 2.3. Stage

Stage обычно используется как репетиция production. Здесь можно воспроизвести реальные способы deployment, сетевую topology, несколько экземпляров сервиса, настоящую СУБД, реальные интеграционные протоколы, health checks и близкую к production конфигурацию.

Но stage почти никогда не совпадает с production полностью.

| Фактор | Stage | Prod |
|---|---:|---:|
| Строк в таблице | 1 000 | 100 000 000 |
| Экземпляров сервиса | 1 | 20 |
| Внешний API | быстрый mock | реальная задержка и квоты |
| Deployment | полная замена | rolling update |

Поэтому фраза «на stage всё прошло» означает только, что сценарий прошёл в условиях stage.

## 2.4. Почему stage может пропустить проблему

Допустим запрос:

```sql
SELECT *
FROM orders
WHERE customer_id = $1;
```

На stage он работает на тысяче строк, а в production — на ста миллионах. Поведение может измениться из-за плана выполнения, статистики, объёма индекса, конкуренции за I/O, cache hit ratio и количества одновременных запросов.

То же самое относится к нагрузке: 10 req/s на stage и 20 000 req/s в production — разные режимы системы.

## 2.5. Rolling update

При rolling update некоторое время одновременно существуют разные версии:

```text
v1
v1
v2
v2
v2
```

Следовательно, старая и новая версии могут одновременно читать одну БД, формат сообщений должен быть совместим, schema migration должна учитывать несколько версий приложения, а изменения API должны переживать переходный период.

### Что важно запомнить

1. Dev, test, stage и prod решают разные задачи.
2. Stage уменьшает риск, но не доказывает эквивалентность production.
3. Объём данных и интенсивность нагрузки меняют поведение системы.
4. Production надо рассматривать как отдельный режим эксплуатации.

---

## 2.6. Окружения проверяют разные гипотезы

Полезная модель: каждое окружение — это не «копия production разного размера», а инструмент для проверки определённых предположений.

```text
Dev   → можно ли быстро разрабатывать и воспроизводить локальные сценарии?
Test  → выполняются ли автоматизированные проверки в контролируемых условиях?
Stage → переживает ли артефакт интеграцию и deployment-процесс?
Prod  → как система ведёт себя при реальной нагрузке и реальных последствиях?
```

Отсюда важный вывод: переход между средами не превращает слабую проверку в сильную автоматически. Если stage не воспроизводит реальный объём данных, он не проверяет работу planner на таком объёме. Если test использует mock внешнего API, он не проверяет его реальные latency и quotas.

### Environment drift

Со временем среды расходятся. Отличаться могут:

- версии PostgreSQL;
- количество реплик;
- feature flags;
- лимиты cgroup;
- сетевые политики;
- TLS certificates;
- настройки connection pool;
- объём и распределение данных.

Поэтому утверждение «у нас stage такой же, как prod» нужно раскладывать на конкретные параметры. Полной идентичности почти никогда нет.

### Почему данные особенно важны

Размер таблицы — только часть картины. Два окружения с одинаковым количеством строк всё равно могут вести себя по-разному, если различается распределение данных.

Например, индекс по `status` полезен по-разному, если на stage значения распределены равномерно, а в production 99.9% строк имеют `status = 'DONE'`.

То есть production realism — это ещё и реализм статистики данных.

### Совместимость во время rolling update

Во время rolling update сервис временно является распределённой системой из нескольких версий собственного кода. Поэтому изменения должны быть совместимы во времени.

Типичный безопасный порядок изменения схемы:

```text
1. добавить новую колонку так, чтобы старая версия продолжала работать
2. развернуть код, умеющий читать/писать новую схему
3. дождаться исчезновения старой версии
4. только потом удалить старую колонку или старый формат
```

Это пример того, как deployment-механика напрямую влияет на дизайн application code и schema migration.

# 3. Артефакт приложения

## 3.1. Исходный код и executable

Исходный код описывает программу:

```text
main.go
handler.go
service.go
repository.go
go.mod
go.sum
```

Но production запускает не Git-репозиторий. Нужен исполняемый результат:

```text
source
↓
compiler
↓
binary
```

Например:

```bash
go build -o app .
```

## 3.2. Что находится внутри Go binary

Обычный Go binary содержит скомпилированный application code, значительную часть используемой standard library и Go runtime.

Runtime отвечает за goroutines, scheduler, garbage collection, stacks, allocation, timers, часть network polling и panic/recover.

Отдельная VM для обычного Go-приложения не требуется, но runtime никуда не исчезает — он поставляется вместе с программой.

## 3.3. Binary не работает «где угодно»

Компиляция имеет target:

```text
GOOS
GOARCH
```

Например:

```bash
GOOS=linux GOARCH=amd64 go build .
```

создаёт binary для Linux/amd64, а:

```bash
GOOS=darwin GOARCH=arm64 go build .
```

— другой binary.

## 3.4. cgo и внешняя среда

При использовании cgo могут появляться dynamic libraries и дополнительные требования к ОС.

Даже статический binary может зависеть от сертификатов, timezone data, filesystem, DNS, базы данных и внешних сервисов.

Поэтому «один бинарник» описывает способ доставки executable, а не отсутствие окружения.

## 3.5. Container image и container

```text
Go binary
↓
container image
↓
container
```

Image — сохранённый артефакт. Container — запущенный экземпляр image.

Важно различать:

```text
Git commit
≠
binary
≠
container image
≠
running container
```

## 3.6. Один артефакт через окружения

Хорошая delivery model:

```text
source
↓
build
↓
artifact
↓
test
↓
stage
↓
prod
```

Плохая схема:

```text
build #1
↓
test OK

build #2
↓
prod
```

Второй build может использовать другую toolchain, dependency, base image, generated code или build flags.

Практический принцип:

> Build once, promote the same artifact.

## 3.7. Идентификация артефакта

Нужно уметь ответить:

- из какого commit собран artifact;
- какой toolchain использовался;
- какие dependencies вошли;
- какие build flags применялись;
- какой image digest развернут.

---

## 3.8. Что именно определяет результат сборки

Git commit — важный вход сборки, но не единственный. На итоговый artifact могут влиять:

```text
source revision
+
Go toolchain version
+
dependency graph
+
build tags / flags
+
GOOS / GOARCH
+
generated sources
+
cgo environment
+
container base image
```

Если любой из этих входов изменился, строго говоря, у нас уже другая сборка.

Именно поэтому версия приложения в production должна связываться не только с Git tag, но и с конкретным binary или image digest.

### Reproducible build и promotion — разные идеи

Есть два связанных, но разных свойства.

**Reproducible build** означает, что одинаковые входы позволяют воспроизвести одинаковый или эквивалентный результат сборки.

**Artifact promotion** означает, что мы вообще не пересобираем приложение между test, stage и prod, а двигаем уже полученный artifact.

Вторая модель проще с точки зрения доказательства: production получает именно то, что проверялось ранее.

### Что даёт контейнерный образ

Image фиксирует больше окружения, чем голый binary:

- базовую файловую систему;
- системные certificates;
- timezone data;
- дополнительные shared libraries;
- entrypoint;
- metadata.

Но image всё равно не содержит PostgreSQL, DNS, сеть и внешние API. Контейнеризация уменьшает часть environmental variability, но не устраняет распределённую природу backend.

# 4. Конфигурация

## 4.1. Конфигурация отделяется от артефакта

Один artifact может работать в разных средах:

```text
TEST:
DATABASE_URL=postgres://test-db/orders

STAGE:
DATABASE_URL=postgres://stage-db/orders

PROD:
DATABASE_URL=postgres://prod-db/orders
```

Binary тот же, параметры разные.

## 4.2. Артефакт, конфигурация и secrets

Артефакт содержит application code и встроенные resources.

Конфигурация задаёт адреса, timeouts, pool sizes и другие параметры поведения.

Secrets — passwords, tokens, private keys — требуют отдельной модели доступа и ротации.

## 4.3. Пример загрузки конфигурации

```go
package main

import (
    "errors"
    "os"
)

type Config struct {
    HTTPAddr    string
    DatabaseURL string
}

func loadConfig() (Config, error) {
    cfg := Config{
        HTTPAddr:    os.Getenv("HTTP_ADDR"),
        DatabaseURL: os.Getenv("DATABASE_URL"),
    }

    if cfg.HTTPAddr == "" {
        cfg.HTTPAddr = ":8080"
    }

    if cfg.DatabaseURL == "" {
        return Config{}, errors.New("DATABASE_URL is required")
    }

    return cfg, nil
}
```

Для `HTTP_ADDR` допустим default. Для обязательного DSN лучше завершиться на старте, чем получить случайный `500` на первом пользовательском запросе.

## 4.4. Валидация

Наличие значения не означает корректность:

```text
DB_POOL_SIZE=-100
```

Нормальная цепочка:

```text
read configuration
↓
parse types
↓
validate ranges
↓
start application
```

### Что важно запомнить

1. Артефакт и environment-specific configuration лучше разделять.
2. Конфигурация должна валидироваться при старте.
3. Secrets требуют отдельной модели безопасности.
4. Корректная строка конфигурации ещё не доказывает доступность внешнего ресурса.

---

## 4.5. Конфигурация имеет жизненный цикл

Конфигурация проходит несколько стадий:

```text
получить значение
↓
преобразовать к типу
↓
проверить диапазон и взаимные ограничения
↓
применить
↓
сделать наблюдаемым факт применения
```

Например, `HTTP_TIMEOUT=abc` — ошибка parsing. `HTTP_TIMEOUT=-5s` может быть синтаксически корректным duration, но логически недопустимым значением. А `DB_POOL_SIZE=10000` может быть формально допустимым integer, но разрушительным для конкретной базы данных.

### Независимая и связанная валидация

Иногда одного диапазона мало:

```text
connect_timeout = 5s
request_timeout = 2s
```

Такой набор может быть нелогичен: полный request timeout меньше времени, которое разрешено потратить только на соединение.

То есть конфигурация может иметь **межпараметрические инварианты**.

### Static и dynamic configuration

Часть настроек обычно читается на старте процесса:

```text
HTTP port
DB DSN
pool size
```

Другие системы могут поддерживать dynamic config без рестарта. Это усложняет модель: нужно понимать, когда изменение становится видимым, все ли goroutines видят его одновременно и что происходит с уже выполняющимися запросами.

Для вводной лекции достаточно основной идеи: конфигурация — такой же вход программы, как request. Её тоже нужно валидировать и наблюдать.

### Secrets нельзя печатать ради удобства диагностики

Очень частая ошибка — логировать полностью загруженную структуру `Config`. Если там есть token или password, observability внезапно становится каналом утечки.

Практический подход: логировать безопасные параметры и факт наличия secret, но не само значение.

```text
DATABASE_HOST=db.prod
DATABASE_PASSWORD=<configured>
```

# 5. Внешние зависимости

## 5.1. За одной строкой скрывается система

```go
resp, err := client.Do(req)
```

За этой строкой могут находиться DNS, connection pool, TCP, TLS, network, remote load balancer, remote application, remote database и обратный путь response.

Количество строк application code ничего не говорит о количестве участвующих подсистем.

## 5.2. Latency превращается в concurrency

Пусть сервис получает 100 requests/s, а средняя операция занимает 0.05 s.

По закону Литтла:

```text
L = λ × W
```

получаем:

```text
100 × 0.05 = 5
```

Если dependency начинает отвечать за 5 s:

```text
100 × 5 = 500
```

Входной поток тот же, но число одновременно находящихся в системе операций выросло в сто раз.

Причинная цепочка:

```text
downstream latency ↑
↓
in-flight requests ↑
↓
goroutines ↑
↓
memory ↑
↓
connections occupied ↑
↓
queueing ↑
↓
overall latency ↑
```

## 5.3. Goroutine не делает downstream бесконечным

Можно создать тысячи goroutines, но база может иметь двадцать соединений, внешний API — quota 100 requests/s, а CPU — конечное количество ядер.

Дешёвая goroutine не увеличивает capacity внешнего ресурса.

## 5.4. Deadline

```go
ctx, cancel := context.WithTimeout(
    r.Context(),
    2*time.Second,
)
defer cancel()
```

Deadline ограничивает время ожидания, но не ограничивает количество одновременно начавшихся операций.

## 5.5. Ограничение concurrency

```go
var slots = make(chan struct{}, 50)

func callDependency(ctx context.Context) error {
    select {
    case slots <- struct{}{}:
        defer func() { <-slots }()
    case <-ctx.Done():
        return ctx.Err()
    }

    return doRequest(ctx)
}
```

Теперь одновременно выполняется не более 50 операций.

## 5.6. Ограниченная очередь

Если incoming rate выше processing capacity, очередь растёт, а вместе с ней memory и latency.

Поэтому очередь должна иметь capacity, а после исчерпания capacity система должна сделать явный выбор: reject, shed load или backpressure.

## 5.7. Retry

Retry создаёт дополнительную нагрузку:

```text
1000 requests
×
до 3 попыток
=
до 3000 обращений
```

При перегрузке легко получить:

```text
overload
↓
errors
↓
retry
↓
more load
↓
more errors
```

Retry policy должна учитывать тип ошибки, количество попыток, backoff, оставшийся deadline и идемпотентность.

### Что важно запомнить

1. Latency внешней системы напрямую увеличивает concurrency внутри сервиса.
2. Timeout и concurrency limit решают разные задачи.
3. Неограниченные очереди скрывают проблему, но не решают её.
4. Retry способен усилить перегрузку.
5. Backend — система ограниченных ресурсов.

---

## 5.8. Timeout, deadline и cancellation — связанные, но разные понятия

Их часто сваливают в одно слово «таймаут».

**Timeout** — длительность, которую мы разрешаем операции.

**Deadline** — абсолютный момент времени, после которого операция уже не нужна.

**Cancellation** — сигнал о том, что работу следует прекратить.

В Go `context.Context` позволяет переносить deadline и cancellation вниз по call chain. Но отмена остаётся кооперативной: вызываемый код должен её поддерживать.

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()

err := repository.Load(ctx, id)
```

Если `repository.Load` игнорирует `ctx`, сам факт наличия context у caller проблему не решает.

## 5.9. Little's Law требует устойчивого режима

Формула:

```text
L = λ × W
```

очень полезна, но её нельзя воспринимать как магический калькулятор для любой перегрузки.

Она хорошо описывает устойчивый поток, когда система находится примерно в стационарном режиме. Если входной поток постоянно выше service capacity, очередь растёт без ограничения и стационарного значения `L` уже нет.

То есть пример `100 req/s × 5 s = 500 in-flight` — полезная инженерная оценка, пока система способна находиться в устойчивом режиме.

## 5.10. Пул соединений — отдельная очередь

Пусть HTTP server принял 500 requests одновременно, а database pool имеет 20 connections.

```text
500 request goroutines
↓
20 выполняют SQL
480 ждут pool
```

PostgreSQL может быть относительно свободна, но latency приложения уже растёт из-за ожидания ресурса внутри самого процесса.

Поэтому при диагностике полезно разделять:

```text
время до получения соединения
+
время выполнения SQL
```

Иначе вся задержка ошибочно будет записана на «медленную базу».

## 5.11. Backpressure

Backpressure — это способность системы ограничить поступление новой работы, когда downstream уже насыщен.

Без backpressure:

```text
incoming work
↓
unbounded goroutines / queue
↓
memory growth
↓
GC pressure
↓
latency growth
↓
OOM или collapse
```

С bounded concurrency:

```text
incoming work
↓
capacity check
↓
есть слот? → выполнить
нет слота? → ждать ограниченно / отклонить
```

Важно: scheduler Go сам по себе backpressure не создаёт. Он умеет планировать runnable goroutines, но не знает capacity PostgreSQL или quota внешнего API.

## 5.12. Retry должен жить внутри общего временного бюджета

Пусть request имеет deadline 2 секунды. Нельзя бездумно выполнить три попытки по 2 секунды каждая — это разрушает исходный SLA.

Более корректная модель:

```text
request deadline
↓
attempt #1 использует часть бюджета
↓
backoff
↓
проверяем остаток времени
↓
attempt #2 только если ещё есть смысл
```

Retry — не способ превратить ненадёжную систему в надёжную. Это инструмент обработки отдельных временных сбоев.

## 5.13. Что измерять у зависимости

Для каждой важной external dependency полезно видеть хотя бы:

- latency;
- error rate;
- timeout count;
- active/in-flight operations;
- pool usage;
- queue/wait time;
- retry count.

Тогда причинная цепочка становится наблюдаемой, а не предполагаемой.

# 6. Почему появился Go

Go начал разрабатываться в 2007 году. Первоначальными авторами дизайна были Robert Griesemer, Rob Pike и Ken Thompson. В 2009 году проект был публично открыт.

Контекст:

```text
большие codebase
+
долгие сборки
+
сложные dependency graph
+
много команд
+
сетевые сервисы
+
многоядерные машины
```

Стоимость создавалась не только выполнением программы, но и самой разработкой: как собрать, как понять зависимости, как читать чужой код, как выражать concurrency и как сопровождать систему годами.

Go проектировался как инженерный компромисс: сравнительно небольшой язык, GC, goroutines, structural interfaces, единый formatter и toolchain.

Простой язык не означает простую систему. Сложность production backend остаётся, просто она не обязательно прячется за большим количеством language features.

---

## 6.1. Язык проектировали вокруг стоимости инженерного процесса

Обычно язык обсуждают через syntax: есть ли классы, generics, exceptions, pattern matching. Для Go полезнее смотреть на другую ось: сколько стоит сопровождение большого проекта большой командой.

Если язык позволяет выразить одну идею двадцатью способами, это повышает выразительность отдельного разработчика, но увеличивает пространство решений, которое должен понимать каждый следующий читатель кода.

Go сознательно делает другой компромисс:

```text
меньше language mechanisms
↓
меньше локальной выразительности
↓
больше единообразия
↓
ниже стоимость чтения и tooling
```

Это не делает Go объективно «лучше» более сложных языков. Это конкретный design trade-off.

## 6.2. Concurrency была встроена в модель языка с самого начала

В конце 2000-х server software уже массово работало с тысячами одновременно ожидающих сетевых операций. Модель «одна задача = один тяжёлый OS thread» плохо масштабировалась по памяти и scheduling overhead.

Go предлагает goroutines и channels как высокоуровневые primitives, а runtime берёт на себя multiplexing goroutines на OS threads.

При этом goroutine не является магией: она потребляет stack, runtime metadata, участвует в GC и scheduler. Это будет предметом следующей лекции.

## 6.3. Tooling — часть языка как платформы

`gofmt`, `go test`, `go vet`, module tooling и build command поставляются как единая экосистема. Это уменьшает количество решений, которые каждая команда вынуждена собирать самостоятельно.

То есть Go — это не только grammar языка. Это комбинация:

```text
language
+
compiler
+
runtime
+
standard library
+
toolchain
```

Именно эту платформу мы и изучаем.

# 7. История Go по релизам

## 7.1. Go 1.0 — 2012

Главное событие — стабилизация платформы и Go 1 compatibility promise.

Закрепились `error`, `rune`, `delete`, структура standard library и использование сравнимых структур и массивов как map keys.

```go
type UserKey struct {
    TenantID int64
    UserID   int64
}

users := map[UserKey]string{}
```

Главная идея: обновление языка не должно регулярно требовать переписывания работающей системы.

### Почему этот релиз фундаментален

До Go 1 язык ещё мог заметно меняться. Для production adoption это серьёзная проблема: бизнес-система живёт годами, а не до следующего compiler release. Go 1 проводит границу между периодом активного поиска языка и периодом долгосрочной совместимости.

Именно отсюда появляется важная философия Go: новые возможности должны по возможности добавляться так, чтобы старый корректный source продолжал жить. Это ограничивает свободу designers, но резко уменьшает стоимость миграций для пользователей языка.

## 7.2. Go 1.1 — 2013

Появился race detector:

```bash
go test -race ./...
```

Он исследует выполненные execution paths. Если опасный сценарий не активирован, отсутствие report ничего не доказывает.

Также улучшались map, inlining, GC и networking runtime integration.

### Почему race detector меняет практику разработки

Race condition часто не проявляется как стабильный bug. Один запуск проходит, второй тоже, а на сотом другая interleaving операций повреждает состояние.

Race detector делает проблему наблюдаемой динамически: инструмент следит за обращениями к памяти и synchronization events во время выполнения. Цена — заметный overhead, поэтому это инструмент test/debug режима, а не обычный production runtime.

Главное ограничение остаётся принципиальным: не выполненный путь невозможно проверить динамически.

## 7.3. Go 1.2 — 2013

Появился full slice expression:

```go
part := source[:2:2]
```

Третий индекс ограничивает capacity, но не копирует элементы.

Появился coverage:

```bash
go test -cover ./...
```

Scheduler получил дополнительные preemption points на function entry, но длинный цикл без вызовов оставался сложным случаем.

### Почему full slice expression важнее, чем кажется

Slice — descriptor над backing array. Контроль `cap` позволяет управлять тем, сможет ли будущий `append` продолжить использовать тот же array.

Это не memory isolation. До тех пор пока два slices адресуют одни и те же элементы backing array, обычная запись остаётся общей. Full slice expression управляет будущим ростом, а не создаёт копию данных.

Изменение scheduler в 1.2 также показывает раннюю проблему Go runtime: concurrency model языка уже существовала, но механизм fairness scheduler ещё продолжал активно развиваться.

## 7.4. Go 1.3 — 2014

Runtime перешёл от segmented stacks к copying contiguous stacks:

```text
small stack
↓
space exhausted
↓
allocate larger stack
↓
copy active frames
↓
continue
```

Это устранило hot stack split.

Появился `sync.Pool` для временного переиспользования объектов. Он не является resource pool: runtime может удалить его содержимое.

### Почему copying stack — архитектурно важное решение

Маленький stack делает goroutine дешёвой только если stack способен расти. Segmented stack решал эту задачу кусками памяти, но создавал expensive boundary crossings.

Copying stack выбирает другой trade-off: редкая дорогая операция копирования в обмен на обычное быстрое выполнение между growth events.

Чтобы это работало, runtime должен понимать, какие значения на stack являются pointers, и уметь корректировать ссылки после relocation. То есть stack growth связан не только со scheduler, но и с compiler metadata и GC.

## 7.5. Go 1.4 — 2014

Начальный stack goroutine был уменьшен с 8 KiB до 2 KiB.

Появились `go generate` и `internal`.

2 KiB — историческая деталь implementation, а не вечная гарантия языка и не полная стоимость goroutine.

### Почему уменьшение initial stack влияет на масштабирование

Если одна goroutine резервирует меньше памяти на старте, процесс может дешевле создать большое количество goroutines. Но initial size нельзя путать с фактическим memory footprint длительно живущей G.

Stack растёт по мере необходимости, сама `g` имеет runtime metadata, а объекты, на которые ссылается goroutine, могут находиться в heap. Поэтому «goroutine стоит 2 KiB» — плохая capacity model.

## 7.6. Go 1.5 — 2015

Появился concurrent GC.

```text
pause time ↓
↓
concurrent GC work ↑
↓
CPU overhead + write barriers
```

`GOMAXPROCS` по умолчанию стал учитывать доступные CPU вместо значения 1.

Больше parallelism могло проявить уже существующие concurrency bugs.

### Почему concurrent GC меняет latency model

Stop-the-world collector концентрирует работу в паузе. Concurrent GC переносит значительную часть работы на время выполнения приложения.

Это улучшает latency pauses, но GC начинает конкурировать с application goroutines за CPU и требует write barriers для корректности concurrent marking.

Следовательно, GC improvement — не исчезновение стоимости memory management, а изменение того, где и как эта стоимость оплачивается.

## 7.7. Go 1.6 — 2016

`net/http` получил автоматическую поддержку HTTP/2 в подходящих HTTPS-соединениях.

Vendoring включён по умолчанию, уточнены cgo pointer rules, runtime начал обнаруживать часть concurrent map misuse.

Обычная `map` не стала concurrency-safe.

### HTTP/2 как пример изменения под API

Handler source может не измениться, но transport behaviour меняется существенно. Несколько logical requests способны идти через одно TCP connection.

Это влияет на connection usage, head-of-line characteristics разных уровней и pattern нагрузки на server. Хороший пример того, что standard library может менять operational behaviour без переписывания business code.

## 7.8. Go 1.7 — 2016

В standard library появился `context`.

```go
ctx, cancel := context.WithTimeout(
    context.Background(),
    time.Second,
)
defer cancel()
```

Context задаёт контракт cancellation, deadline и request-scoped values.

Cancellation кооперативна: `cancel()` не уничтожает goroutine.

Также появился SSA backend compiler.

### Context — управление жизненным циклом работы

До появления общего `context` каждый library/API мог изобретать собственную модель timeout и cancellation. Standard contract позволил передавать lifetime request через несколько слоёв приложения.

Но context не является механизмом принудительного прерывания. Если функция выполняет бесконечный CPU loop и никогда не проверяет cancellation, context сам её не остановит.

Поэтому cancellation в Go — протокол сотрудничества между caller и callee.

## 7.9. Go 1.8 — 2017

Появился `http.Server.Shutdown(ctx)` для graceful HTTP shutdown.

`database/sql` получил context-aware operations.

Появились mutex profiles.

Shutdown HTTP server не завершает автоматически все фоновые goroutines приложения.

### Graceful shutdown — не просто `Close()`

Production service должен перестать принимать новую работу, дать ограниченное время уже принятым requests и затем освободить ресурсы.

`Server.Shutdown` стандартизирует HTTP-часть процесса, но application lifecycle обычно шире: background consumers, timers, message handlers и собственные goroutines требуют отдельного управления.

Это важное ограничение abstraction: библиотека управляет только теми ресурсами, которыми владеет сама.

## 7.10. Go 1.9 — 2017

Появились type aliases:

```go
type User = model.User
```

`time.Time` получил monotonic component для измерения durations.

Появился `sync.Map`, но он не делает атомарной произвольную последовательность `Load → logic → Store`.

### Monotonic time закрывает реальную production-проблему

Wall clock может измениться из-за NTP correction или ручного перевода времени. Если измерять latency простым вычитанием wall-clock timestamps, можно получить странные результаты.

Monotonic component позволяет `time.Since` измерять elapsed duration независимо от таких изменений.

Это хороший пример маленького API change с большим operational смыслом.

## 7.11. Go 1.10 — 2018

Улучшилось кеширование build и successful test results.

Для принудительного повторного запуска:

```bash
go test -count=1 ./...
```

Появился `strings.Builder`.

### Скорость обратной связи — часть engineering performance

Если полный build/test занимает долго, разработчики реже запускают проверки и позже получают feedback. Build cache уменьшает стоимость повторной работы.

Но кеширование требует понимать его contract: иногда нужен реальный повтор integration test, и тогда используется `-count=1`.

## 7.12. Go 1.11 — 2018

Появилась предварительная поддержка Go Modules.

`go.mod` начал описывать module и requirements, dependency management стал отделяться от GOPATH.

### Modules решают проблему идентичности dependency

GOPATH хорошо работал в ранней экосистеме, но плохо выражал вопрос «какая именно версия этой библиотеки нужна проекту».

Module делает dependency version частью явной модели build. Это фундамент для reproducibility, но одновременно добавляет правила versioning, module paths и private access.

## 7.13. Go 1.12 — 2019

Продолжились improvements timers, network deadlines и memory behaviour.

На Linux runtime начал использовать `MADV_FREE`.

Это объясняет, почему Go heap может уменьшиться, а RSS некоторое время оставаться высоким.

### Почему RSS и Go heap расходятся

Освободить объект для GC, освободить runtime span и вернуть physical pages операционной системе — разные события.

Поэтому диагностика memory leak должна смотреть на несколько уровней. Один высокий RSS без анализа heap profile и runtime metrics недостаточен для вывода об утечке.

## 7.14. Go 1.13 — 2019

Появилась современная error wrapping model:

```go
return fmt.Errorf("load user %d: %w", id, err)
```

```go
if errors.Is(err, sql.ErrNoRows) {
    // ...
}
```

Появился `errors.As`.

TLS 1.3 включён по умолчанию, module proxy и checksum database стали стандартной частью module ecosystem.

### Error wrapping сохраняет два уровня информации

До `%w` разработчик часто выбирал между двумя плохими вариантами: вернуть original error без контекста или создать красивый текст и потерять machine-readable cause.

Wrapping позволяет иметь оба уровня:

```text
человеческий контекст
+
программно распознаваемая причина
```

Но если внешний caller начинает зависеть от конкретной wrapped error через `errors.Is`, внутренняя ошибка фактически становится частью observable API contract.

## 7.15. Go 1.14 — 2020

Появилась asynchronous preemption.

CPU-bound goroutine без cooperative scheduling points стало проще вытеснять, что улучшило progress scheduler и GC.

Многие случаи `defer` стали дешевле.

### Почему async preemption понадобилась вообще

Scheduler Go управляет goroutines на ограниченном количестве execution resources. Если CPU-bound G слишком долго не отдаёт управление, страдают другие goroutines и GC.

Asynchronous preemption добавляет runtime возможность прервать выполнение в большем числе точек. Это улучшает fairness, но Go всё равно не становится real-time системой: точный момент исполнения goroutine не гарантируется.

## 7.16. Go 1.15 — 2020

Улучшился linker: снизились build time и linker memory.

Появился `time/tzdata`.

Изменения TLS certificate validation могли проявить устаревшие сертификаты без изменения business code.

### Security rules тоже являются частью platform evolution

Изменение certificate validation показывает важную границу compatibility: сохранение старого небезопасного поведения не является абсолютной ценностью.

Production upgrade нужно проверять на реальных integration contracts, потому что compiler/runtime/standard library взаимодействуют с внешним миром, который может опираться на устаревшие assumptions.

## 7.17. Go 1.16 — 2021

Появился `embed`:

```go
import "embed"

//go:embed templates/*.html
var templates embed.FS
```

Можно связывать templates, static files и другие resources с binary.

Secrets так хранить нельзя.

Modules стали default mode, появилась поддержка Apple Silicon.

### `embed` уменьшает риск рассинхронизации артефактов

Без embedding executable и templates могут поставляться отдельно. Тогда возможна ситуация: binary обновили, а directory с templates осталась старой.

Embedding связывает versions этих ресурсов. Цена — изменение embedded file требует пересборки binary, а сам binary становится больше.

## 7.18. Go 1.17 — 2021

На основных amd64-платформах появился register-based calling convention.

Для safe Go source это почти прозрачно, но runtime performance может измениться без изменения исходников.

Также появились `//go:build`, `unsafe.Add`, `unsafe.Slice`, module graph pruning и lazy loading.

### Calling convention показывает силу скрытых implementation changes

Application source не меняется, но compiler иначе передаёт arguments между functions. Это уменьшает часть memory traffic и overhead вызовов.

Такие изменения особенно хорошо показывают смысл Go 1 promise: source API стабилен, а implementation под ним продолжает эволюционировать.

## 7.19. Go 1.18 — 2022

Появились generics:

```go
func Contains[T comparable](items []T, target T) bool {
    for _, item := range items {
        if item == target {
            return true
        }
    }
    return false
}
```

Также появились `any`, `comparable`, fuzzing и `go.work`.

### Generics расширяют язык, сохраняя static typing

До 1.18 повторно используемый type-safe algorithm часто требовал duplication или code generation. `interface{}` снимал часть duplication, но переносил type checks в runtime и ухудшал API clarity.

Type parameters позволяют compiler сохранить связь input/output types на этапе компиляции.

Цена — type system становится сложнее, а library authors получают новый способ создавать как полезные abstractions, так и чрезмерно сложные API.

## 7.20. Go 1.19 — 2022

Появился `GOMEMLIMIT` и `debug.SetMemoryLimit`.

Это soft runtime memory limit, а не жёсткий RSS limit.

Появились typed atomics:

```go
var counter atomic.Int64
counter.Add(1)
```

Уточнена Go Memory Model.

### GOMEMLIMIT — попытка связать GC с реальным memory budget

До memory limit основной tuning GC строился вокруг отношения объёма heap между cycles. В контейнере реальный вопрос другой: сколько памяти вообще разрешено процессу.

`GOMEMLIMIT` даёт runtime ориентир, но не является жёстким process limit и не отменяет live data. Если приложение действительно удерживает слишком много достижимых объектов, GC не сможет их освободить.

## 7.21. Go 1.20 — 2023

Появился `errors.Join`, а также `context.WithCancelCause` и `context.Cause`.

PGO появилась в предварительном виде:

```text
run workload
↓
collect profile
↓
build using profile
↓
compiler optimizes hot paths
```

### Cause cancellation улучшает диагностику lifecycle

Раньше факт `context canceled` сообщал, что работа отменена, но плохо объяснял почему. Cause позволяет передать более содержательную причину.

Для distributed backend это важно: одинаковый симптом cancellation может означать client disconnect, exceeded deadline, shutdown или отмену бизнес-операции.

## 7.22. Go 1.21 — 2023

Появились generic packages `slices`, `maps`, `cmp`.

В язык вошли `min`, `max`, `clear`.

Появился `log/slog`.

PGO стала пригодна для общего использования.

Появился современный механизм toolchain selection.

### Toolchain становится управляемой частью module workflow

Автоматический выбор toolchain уменьшает friction разработки: module может требовать более новую версию Go, а tool способен подобрать её автоматически.

Но convenience локальной разработки превращается в dependency CI на наличие нужной toolchain или возможности её скачать. Поэтому production build pipeline должен явно контролировать эту часть environment.

## 7.23. Go 1.22 — 2024

Изменилась semantics loop variables.

Классический код:

```go
for _, user := range users {
    go func() {
        process(user)
    }()
}
```

в новом language mode получает отдельную declared variable для каждой iteration.

Появился range по integer и расширенный `ServeMux`:

```go
mux.HandleFunc("GET /users/{id}", handler)
```

### Изменение loop variable чинит старый semantic trap

Старая semantics позволяла closure захватить одну переменную, значение которой менялось между iterations. Ошибка особенно часто проявлялась с goroutines, потому что execution происходило позже.

Новая semantics уменьшает класс bugs на уровне языка. Но shared objects внутри переменной по-прежнему остаются shared: новая loop variable не делает deep copy данных.

## 7.24. Go 1.23 — 2024

Появился range-over-function и package `iter`.

Изменилась реализация timers: недостижимые `Timer` и `Ticker` могут освобождаться GC, усилились гарантии `Stop` и `Reset`.

Появился package `unique`.

### Iterators без обязательной goroutine

Range-over-function позволяет описывать последовательность как protocol вызовов, не создавая промежуточный slice и не используя channel только ради iteration.

Это важный design point: channel — synchronization primitive, и использовать его как универсальный iterator не всегда выгодно.

## 7.25. Go 1.24 — 2025

Map implementation перешла на Swiss Tables.

Language semantics осталась прежней, хотя internal algorithm изменился.

Также появились generic aliases, `tool` directive, `testing.B.Loop`, `os.Root`, `weak` и `AddCleanup`.

### Swiss Tables — изменение внутренностей с сохранением surface API

Map остаётся тем же language construct, но внутренний алгоритм хранения и lookup меняется ради performance characteristics.

Это ещё один пример: оптимизация runtime может быть гораздо важнее нового syntax для конкретного backend, хотя в source diff нет ни одной строки.

## 7.26. Go 1.25 — 2025

Runtime стал учитывать Linux cgroup CPU bandwidth limit при выборе default `GOMAXPROCS`.

Это снизило риск избыточного parallelism и cgroup throttling внутри контейнеров.

Также появились `WaitGroup.Go`, стабильный `testing/synctest` и Trace FlightRecorder.

### Container-aware GOMAXPROCS закрывает leakage abstraction

Контейнер может видеть множество CPU host, но иметь CPU quota, эквивалентную нескольким ядрам по времени. Если runtime ориентируется только на видимые CPUs, он создаёт слишком много parallel work относительно разрешённого budget.

Container-aware default уменьшает oversubscription и throttling. Но CPU quota всё равно остаётся budget времени, а не гарантией физически выделенных cores.

## 7.27. Go 1.26 — 2026

Green Tea GC стал default garbage collector.

Основные цели — locality, эффективная работа с большим количеством small objects и scalability GC.

Появился синтаксис:

```go
new(100)
```

Продолжились improvements generics, `go fix`, cgo и goroutine leak diagnostics.

### Green Tea GC оптимизирует то, что backend обычно не пишет вручную

Application developer не вызывает collector напрямую, но allocation pattern сервиса формирует его нагрузку. Улучшение locality и обработки small objects может снизить GC overhead без изменений application source.

Однако общий speedup всегда ограничен долей времени, которую приложение вообще тратило на GC. Это обычный закон оптимизации: ускорение одного компонента не может бесконечно ускорять всю систему.

## 7.28. Go 1.27 — 2026

В материале рассматривается ветка Go 1.27 как текущая.

Ключевые изменения:

- методы могут объявлять собственные type parameters;
- JSON v2 и `jsontext` становятся общедоступными;
- goroutine leak diagnostics выходят из экспериментального состояния;
- появляется UUID package;
- продолжаются improvements small allocations;
- SIMD остаётся experimental.

Для свежих runtime changes важно отделять подтверждённый механизм от широких production-выводов.

---

### Свежая версия требует особенно аккуратных выводов

У нового API можно описать documented contract сразу, но реальные production trade-offs проявляются только после эксплуатации на разных workloads.

Поэтому для свежих возможностей полезно разделять:

```text
что гарантирует документация
что делает текущая implementation
что измерено на нашем workload
что пока является ожиданием
```

Это правило применимо ко всему курсу, особенно к runtime internals.

# 9. Go 1 Compatibility Promise

Compatibility promise создаёт долгосрочный контракт.

Упрощённо:

> Корректный Go 1 source должен продолжать компилироваться и работать с последующими Go 1 releases, кроме оговорённых исключений.

Но promise не фиксирует:

- производительность;
- количество allocations;
- scheduler internals;
- GC algorithm;
- exact scheduling;
- binary format;
- compiler optimizations;
- runtime implementation.

Поэтому correct result может сохраниться, а latency, memory и CPU измениться.

Обновление toolchain всё равно требует:

```text
compile
↓
tests
↓
race tests
↓
integration tests
↓
benchmarks/load tests
↓
production metrics
```

---

## 9.1. Совместимость исходников не означает заморозку платформы

Это один из центральных design principles Go. Проект старается позволить старому корректному source code продолжать работать, одновременно меняя внутренности compiler и runtime.

Именно поэтому возможна такая ситуация:

```text
тот же source
↓
новая версия Go
↓
другой machine code
↓
другая GC implementation
↓
другое scheduling behaviour
↓
тот же предусмотренный программой результат
```

Compatibility promise защищает разработчика от постоянной миграции syntax/API, но оставляет implementers пространство для оптимизации runtime.

## 9.2. На что нельзя опираться как на контракт

Если приложение корректно работает только потому, что goroutines «обычно» запускаются в определённом порядке, оно уже содержит ошибку design.

То же относится к зависимости от:

- конкретного времени GC pause;
- случайного порядка `map` iteration;
- точного количества OS threads;
- внутренней структуры scheduler;
- конкретного allocation behaviour compiler.

Это либо implementation details, либо поведение, которое нужно измерять, а не считать гарантией языка.

## 9.3. Практический смысл при обновлении Go

Обновление toolchain имеет два независимых вопроса:

```text
1. сохранилась ли логическая корректность?
2. сохранились ли приемлемые operational characteristics?
```

Первый проверяется tests и compatibility contract. Второй — benchmark, load testing и production telemetry.

# 10. Go Modules

## 10.1. Package, module и repository

Package — единица импорта и организации кода.

Module — версионируемый набор packages.

Repository — хранилище исходников, которое может содержать один или несколько modules.

```text
package ≠ module ≠ repository
```

## 10.2. `go.mod`

```go
module example.org/shop

go 1.27

require (
    example.org/database v1.5.0
)
```

`go.mod` описывает module и dependency requirements.

## 10.3. `go.sum`

`go.sum` хранит cryptographic checksums содержимого modules и metadata.

Он не является обычным lock-file.

## 10.4. Minimal Version Selection

Пусть:

```text
A requires C v1.3.0
B requires C v1.5.0
```

Приложение требует A и B.

Минимальная версия C, удовлетворяющая всему graph:

```text
C v1.5.0
```

Это ключевая идея MVS.

## 10.5. Major versions

Для `v2+` module path обычно содержит major suffix:

```text
example.org/lib
example.org/lib/v2
```

Для Go это разные module paths.

## 10.6. Private modules

Например:

```bash
GOPRIVATE=git.example.org/*
```

Эта настройка сообщает toolchain, что соответствующие module paths требуют private handling.

### Что важно запомнить

1. Module — не package и не repository.
2. `go.mod` описывает requirements.
3. `go.sum` хранит checksums.
4. MVS выбирает минимальные versions, удовлетворяющие всему graph.
5. Major version может быть частью module path.

---

## 10.7. Dependency graph — это граф, а не плоский список

Если ваш `go.mod` содержит пять прямых dependencies, итоговая программа может зависеть от десятков transitive modules.

```text
application
├── A
│   ├── C
│   └── D
└── B
    └── C
```

Поэтому вопрос «какая версия C используется?» решается не чтением одной строки, а построением module graph и применением правил MVS.

Полезные команды:

```bash
go list -m all
go mod graph
go mod tidy
```

`go list -m all` показывает выбранные modules, `go mod graph` помогает увидеть requirements graph, а `go mod tidy` приводит `go.mod` и `go.sum` в соответствие с реально импортируемыми packages и требованиями module.

## 10.8. MVS пошагово

Пусть приложение требует:

```text
A v1.0
B v1.0
```

A требует:

```text
C v1.3
```

B требует:

```text
C v1.5
```

Для module path C build list выбирает `v1.5`, потому что она удовлетворяет обоим minimum requirements.

Важно: MVS не ищет «самую новую версию в интернете». Если граф требует максимум `v1.5`, наличие `v1.9` само по себе не заставляет build выбрать `v1.9`.

Это принципиально отличает MVS от resolver'ов, ориентированных на поиск наиболее свежей версии в допустимом range.

## 10.9. Почему `go.sum` не lock-file

Lock-file обычно мыслят как полную фиксацию конкретного resolved graph. `go.sum` выполняет другую основную функцию: хранит checksums модулей, которые toolchain видел и должен уметь проверять.

Поэтому наличие строки в `go.sum` не означает, что именно этот module обязательно входит в текущую сборку.

## 10.10. Semantic Import Versioning

Для несовместимой major version путь становится частью identity module:

```text
example.org/lib
example.org/lib/v2
```

Это позволяет зависимостям использовать разные major versions одновременно, потому что для Go это разные import/module paths.

Цена — major upgrade становится видимым в source imports.

# 11. Generics

## 11.1. Зачем они появились

До Go 1.18 общий алгоритм для разных типов часто требовал duplication, code generation или `interface{}`.

Generics добавили type parameters.

## 11.2. Простой пример

```go
func Contains[T comparable](
    items []T,
    target T,
) bool {
    for _, item := range items {
        if item == target {
            return true
        }
    }

    return false
}
```

Использование:

```go
hasID := Contains(
    []int{10, 20, 30},
    20,
)

hasEnv := Contains(
    []string{"dev", "stage", "prod"},
    "prod",
)
```

## 11.3. Constraints

`T` — type parameter.

`comparable` — constraint, разрешающий операции `==` и `!=`.

Compiler проверяет допустимость операций статически.

## 11.4. `any`

```go
func First[T any](items []T) (T, bool) {
    var zero T

    if len(items) == 0 {
        return zero, false
    }

    return items[0], true
}
```

`any` подходит, когда алгоритм не требует специфических операций над типом.

## 11.5. Когда generics полезны

Хороший случай:

```text
одинаковый алгоритм
+
разные типы
```

Например containers, reusable algorithms, collection helpers и common data structures.

Если domain invariants и lifecycle различаются, generic abstraction может только скрыть реальные различия.

### Что важно запомнить

1. Generics полезны прежде всего для повторно используемых алгоритмов.
2. Constraints задают допустимые операции.
3. Generic abstraction должна уменьшать реальную сложность.
4. Наличие generics не означает, что ими нужно оборачивать каждый слой приложения.

---

## 11.6. Type parameter — это неизвестный конкретный тип с известными возможностями

В generic function compiler не знает заранее конкретный `T`, но знает constraint.

```go
func Max[T constraints.Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}
```

Ментальная модель:

```text
T может быть разным
но операции над T ограничены constraint
```

То есть generic code остаётся statically typed. Мы не теряем проверку типов ради повторного использования алгоритма.

## 11.7. `any` не даёт операций над значением

`any` означает: конкретный тип может быть любым.

Это не означает, что внутри generic function можно выполнять над `T` любые операции.

```go
func F[T any](a, b T) bool {
    // return a == b // нельзя для произвольного T
    return false
}
```

Для `==` нужен как минимум `comparable`.

Так constraints превращаются в compile-time contract generic algorithm.

## 11.8. Type inference

Во многих вызовах type arguments можно не указывать явно:

```go
Contains([]int{1, 2, 3}, 2)
```

Compiler выводит `T = int` из arguments.

Явная форма тоже возможна:

```go
Contains[int]([]int{1, 2, 3}, 2)
```

Обычно она нужна только тогда, когда inference недостаточен или явное указание улучшает читаемость.

## 11.9. Generics не заменяют polymorphism поведения

Если нужно выбрать реализацию поведения по набору методов, interface по-прежнему естественен.

Если нужен один и тот же алгоритм для множества типов, generics часто естественнее.

Поэтому вопрос выбора механизма начинается не с «что современнее», а с формы задачи:

```text
общий алгоритм над разными типами → type parameters
общий контракт поведения → interface
один конкретный сценарий → обычная функция
```

# 12. Go Toolchain

Go объединяет базовые engineering operations в единый toolchain.

## 12.1. Версия

```bash
go version
```

## 12.2. Environment

```bash
go env
go env GOTOOLCHAIN
```

## 12.3. Форматирование

```bash
go fmt ./...
```

Formatter изменяет оформление source code, но ничего не говорит о business correctness.

## 12.4. Static analysis

```bash
go vet ./...
```

`go vet` ищет подозрительные конструкции. Это полезная эвристическая проверка, но не доказательство корректности.

## 12.5. Tests

```bash
go test ./...
```

Для принудительного повторного запуска:

```bash
go test -count=1 ./...
```

## 12.6. Race detector

```bash
go test -race ./...
```

Отсутствие race report означает только, что на выполненных execution paths race не обнаружена.

## 12.7. Build

```bash
go build -o bin/server ./cmd/server
```

Metadata binary:

```bash
go version -m ./bin/server
```

---

## 12.8. Toolchain — часть воспроизводимости

Когда мы говорим «собрали приложение», важно знать, **чем** оно было собрано.

Разные версии compiler могут генерировать разный machine code, менять inlining, escape decisions, GC/runtime behaviour и performance characteristics.

Поэтому версия Go — такой же build input, как dependencies.

## 12.9. `go test` проверяет только написанные свойства

Успешный test suite означает:

```text
выполненные tests
+
их assertions
→ прошли
```

Он не доказывает correctness поведения, для которого тестов нет.

А race detector дополнительно зависит от executed schedules и paths. Поэтому сильный test suite — это не просто высокое coverage, а набор сценариев, действительно воспроизводящих важные interactions.

## 12.10. `go vet` — не compiler и не theorem prover

`go vet` анализирует известные suspicious patterns. Он полезен именно как дополнительный слой диагностики.

Правильная цепочка выглядит скорее так:

```text
compiler catches type/syntax errors
↓
vet catches suspicious constructs
↓
tests verify expected behaviour
↓
race detector observes concurrent accesses
↓
benchmarks/load tests measure performance
```

Каждый инструмент закрывает свой класс рисков.

# 13. Версия языка и версия toolchain

В `go.mod`:

```go
module example.org/shop

go 1.27
```

`go` directive задаёт минимальную версию Go для module и влияет на language semantics.

Она не означает точную фиксацию patch-version compiler.

Современный Go поддерживает `toolchain` directive и управление через:

```bash
go env GOTOOLCHAIN
```

Toolchain selection может автоматически подбирать подходящую version.

Для закрытого CI это означает, что необходимые toolchains должны быть заранее доступны, иначе automatic download может оказаться невозможен.

---

## 13.1. Почему это вообще разделили

Module может декларировать language baseline, а реально установленный или автоматически выбранный toolchain может быть новее.

Это позволяет использовать современный compiler для сборки module, не включая автоматически semantics более новой версии языка там, где они зависят от `go` directive.

Практически это означает, что при расследовании сборки нужно знать как минимум:

```text
версию языка module
+
реально выбранную toolchain
```

Одна строка `go version` на ноутбуке разработчика ещё не всегда описывает toolchain, которую выбрал конкретный build environment.

# 14. Что должен фиксировать CI

Для воспроизводимого build важно знать:

- source revision;
- Go toolchain version;
- module graph;
- build flags;
- target OS/arch;
- base image;
- generated files;
- artifact digest.

Git commit сам по себе не всегда описывает весь результат сборки.

# 17. Что важно запомнить после лекции

## Production

- Production определяется реальными последствиями.
- Happy path проверяет только один сценарий.
- Ошибка ответа не означает отсутствие side effect.
- Timeout означает прекращение ожидания, а не доказательство отмены операции.

## Окружения

- Dev, test, stage и prod решают разные задачи.
- Stage снижает риск, но не копирует production полностью.
- Объём данных и нагрузка принципиально меняют поведение.

## Артефакт

- Source code и executable artifact — разные сущности.
- Binary, image и running container — разные уровни.
- Лучше продвигать один и тот же artifact между окружениями.

## Конфигурация

- Environment-specific параметры должны быть отделены от артефакта.
- Конфигурацию нужно валидировать при старте.
- Secrets требуют отдельного контроля.

## Внешние зависимости

- Latency увеличивает число in-flight operations.
- Goroutine не увеличивает capacity базы или внешнего API.
- Timeout ограничивает время.
- Semaphore/pool ограничивает concurrency.
- Bounded queue ограничивает накопление работы.
- Retry способен усилить перегрузку.

## История Go

- Go развивается как платформа, а не только как syntax.
- Важные изменения происходят в runtime, GC, scheduler, compiler и toolchain.
- Новая версия может изменить production behaviour без изменения application source.

## Compatibility

- Go 1 compatibility прежде всего защищает source compatibility.
- Performance и runtime internals не фиксируются.
- Toolchain update всё равно требует tests и measurements.

## Modules

- `package != module != repository`.
- `go.mod` описывает requirements.
- `go.sum` хранит checksums.
- MVS выбирает минимальные versions, удовлетворяющие всему graph.

## Generics

- Полезны, когда алгоритм одинаковый, а типы разные.
- Constraints определяют допустимые операции.
- Абстракция должна уменьшать сложность.

## Toolchain

```text
fmt
↓
vet
↓
test
↓
race
↓
build
↓
artifact inspection
```

У каждого инструмента есть своя область проверки.
