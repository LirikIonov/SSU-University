# Правила Markdown под MkDocs Material

Эти правила определяют техническое оформление исследовательской базы под MkDocs Material.

## Структура проекта

Рекомендуемая структура:

```text
knowledge/
├── mkdocs.yml
├── rules/
│   ├── research-markdown.md
│   └── mkdocs-markdown.md
├── scripts/
├── memory/
│   ├── games/
│   ├── personal/
│   └── technology/
└── site/
```

Назначение:

### `mkdocs.yml`

Главный конфигурационный файл MkDocs.

Содержит:
- тему;
- навигацию;
- плагины;
- Markdown extensions;
- настройки TOC;
- настройки поиска.

### `memory/`

Исходники базы знаний. Это `docs_dir`.

Внутри находятся только материалы, которые являются частью базы.

### `memory/games/`

Игровая часть базы:
- компании;
- игровые серии;
- отдельные игры;
- разработчики;
- история индустрии;
- игровые технологии, если они рассматриваются в игровом контексте.

Пример:

```text
memory/games/
├── index.md
├── valve/
│   ├── index.md
│   ├── 01-origins-steam.md
│   ├── 02-games-and-engines.md
│   ├── 03-inside-valve.md
│   ├── 04-hardware-linux-vr.md
│   ├── 05-modern-valve.md
│   ├── 06-valve-as-institution.md
│   └── 07-appendices.md
├── id-software/
└── doom/
```

### `memory/personal/`

Личная база пользователя:
- личные заметки;
- история;
- собственные списки;
- предпочтения;
- другие личные материалы, предназначенные для просмотра через MkDocs.

### `memory/technology/`

Техническая база общего назначения:
- языки программирования;
- архитектура;
- ОС;
- hardware;
- сети;
- runtime;
- другие технические темы, не являющиеся частью конкретного рабочего проекта.

### `scripts/`

Вспомогательные скрипты сборки и обслуживания базы.

Если это исполняемый код, каталог должен находиться вне `memory/`, поскольку `memory/` является `docs_dir`.

### `rules/`

Правила ведения базы.

Каталог находится вне `memory/`, поэтому сами инструкции не публикуются как страницы энциклопедии.

### `site/`

Результат `mkdocs build`. Это `site_dir`.

Файлы внутри него генерируются автоматически и не редактируются руками.

Источником истины всегда является `memory/`.

## Организация тематических разделов

Большую тему хранить в собственной папке:

```text
memory/games/valve/
```

В ней должен быть `index.md` и несколько смысловых томов.

Разбивать материал по смыслу, а не механически по одинаковому количеству пунктов.

Например:

```text
valve/
├── index.md
├── 01-origins-steam.md
├── 02-games-and-engines.md
├── 03-inside-valve.md
├── 04-hardware-linux-vr.md
├── 05-modern-valve.md
├── 06-valve-as-institution.md
└── 07-appendices.md
```

`index.md` используется как навигационная страница темы.

Он содержит:
- короткое описание;
- карту разделов;
- ссылки на тома;
- при необходимости краткую хронологию.

Он не должен дублировать основной текст томов.

## Иерархия заголовков

На каждой странице использовать один `#`.

```markdown
# IV. Hardware, Linux и VR
```

Основные пункты исследования:

```markdown
## 50. Steam Controller { #p050 }
```

Внутренние подразделы:

```markdown
### Главная задача
### Steam Input
### Почему устройство не взлетело
### Мнение Кирилла
```

Более глубокая вложенность:

```markdown
#### Trackpads
#### Gyro
```

Правило:

```text
#     страница / том
##    основной пункт исследования
###   подраздел
####  деталь подраздела
```

## Правый TOC

База рассчитана на:

```yaml
markdown_extensions:
  - attr_list
  - toc:
      toc_depth: 2
      permalink: true
```

Поэтому в правом содержании MkDocs должны отображаться только `##`.

Если там должны быть только пункты 1–100, никакие внутренние разделы не должны получать уровень `##`.

Не использовать на такой странице:

```markdown
## Оглавление
## Введение
## Вывод
```

если эти элементы не должны находиться справа.

Использовать `###` либо вынести их в `index.md`.

## Якоря

Основные пункты получают стабильные ID:

```markdown
## 1. Основание Valve { #p001 }
## 2. Гейб Ньюэлл и Майк Харрингтон { #p002 }
## 81. Владение Valve { #p081 }
## 100. Steam Frame { #p100 }
```

Якорь основного пункта после создания не менять.

Дополнительные темы получают читаемые якоря:

```markdown
## Aperture Hand Lab { #aperture-hand-lab }
## Destinations и SteamVR Home { #destinations-steamvr-home }
```

Не использовать автоматически сгенерированные ID вроде:

```text
sec-000001
sec-000002
```

Не вставлять отдельный HTML-якорь:

```html
<a id="p050"></a>
```

если можно использовать:

```markdown
## 50. Steam Controller { #p050 }
```

## Ссылки между файлами

Использовать относительные Markdown-ссылки:

```markdown
[Steam Controller](04-hardware-linux-vr.md#p050)
```

Для соседней тематической папки:

```markdown
[Half-Life](../half-life/index.md)
```

Не использовать:
- абсолютные пути файловой системы;
- `file:///`;
- `/Users/...`;
- ссылки на временные рабочие файлы.

## Форматирование

Основной материал писать связным текстом.

Не превращать всю статью в набор bullet lists.

Использовать:
- `**важный термин**`;
- `inline code` для файлов, команд, API и идентификаторов;
- fenced code blocks для кода и схем.

## Схемы

Причинные и архитектурные схемы оформлять как:

```text
Windows game
↓
Proton
↓
SteamOS
```

Для таких схем использовать язык `text`.

## Код

Для настоящего кода указывать корректный язык:

```java
...
```

```go
...
```

```yaml
...
```

Не указывать случайный язык подсветки.

## Таблицы

Использовать таблицы только для компактного сравнения однородных данных:

```markdown
| Продукт | Год | Роль |
| --- | ---: | --- |
| Steam Controller | 2015 | Input experiment |
| Steam Deck | 2022 | Handheld platform |
```

Длинный рассказ в таблицу не превращать.

## Admonitions

При включённых расширениях Material допустимы:

```markdown
!!! note "Мнение Кирилла"

    Portal 1 — лучшая игра Valve для Кирилла.
```

```markdown
!!! warning "Важно"

    VAC и VACnet — разные системы.
```

Для необязательных подробностей:

```markdown
??? info "Технические подробности"

    Дополнительный технический материал.
```

Использовать умеренно.

## Большие темы

Если файл становится слишком большим, разбивать его на смысловые тома.

Плохо:

```text
part-1.md
part-2.md
part-3.md
```

только потому, что каждый файл должен содержать по 20 пунктов.

Лучше:

```text
01-origins-steam.md
02-games-and-engines.md
03-inside-valve.md
04-hardware-linux-vr.md
```

Название файла должно объяснять его содержание.

## Служебные данные

В итоговые статьи не включать:
- информацию о процессе генерации;
- результаты validation scripts;
- количество строк;
- названия временных исходников;
- инструкции модели;
- технические комментарии сборки.

## Проверка перед сохранением

Проверить:

1. На странице ровно один `#`.
2. Основные пункты имеют `##`.
3. Внутренние подразделы имеют `###` или ниже.
4. Все стабильные якоря уникальны.
5. Нумерация не имеет случайных дыр.
6. Относительные ссылки ведут на существующие файлы.
7. Ссылки на `#anchor` ведут на существующие якоря.
8. Правый TOC не засорён внутренними подразделами.
9. В тексте нет служебной информации сборки.
10. Файл корректно отображается в MkDocs Material.
